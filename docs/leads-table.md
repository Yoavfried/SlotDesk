# Onboarding leads table — agreed scope

Agreed 15 October 2026. **Implemented in the 0.9.0 preview; central submission is configured.** Save one private lead record for each user who completes onboarding. Email, name and assigned timezone are supplied directly by that user; onboarding completion time is generated by SlotDesk. The owner clarified this provenance explicitly. Intended uses are product/onboarding analysis and possible future first-party project updates where the user opts in. No specific campaign is planned.

## Requested record

| Field | Meaning |
| --- | --- |
| email | The email supplied directly by the onboarding user. |
| name | The name supplied directly by the onboarding user. |
| timezone | The assigned IANA timezone supplied directly by the onboarding user. |
| onboarded_at | SlotDesk-generated UTC timestamp when onboarding completes. |
| updates_opt_in | Boolean recording whether the user checked the optional updates box; false by default. |

These are the five agreed columns. Create the lead regardless of whether the updates box is checked. The checkbox controls permission for future project updates, not whether the lead is recorded. Repeated app openings/retries should not duplicate the lead or replace the initial onboarding timestamp.

## Agreed onboarding UX

Display a short notice with an accessible Privacy Notice link:

> We store your email, name, chosen timezone and setup date to understand SlotDesk registrations and improve the product. See our Privacy Notice.

Display an optional checkbox, unchecked by default:

> You may email me occasional updates about SlotDesk and our future projects. I can opt out at any time.

Users can finish onboarding with the box unchecked. Store the checked value in `updates_opt_in`. This feature is the agreed leads table and onboarding notice/checkbox; it does not add a separate signup flow or mailing system.

## Implementation and activation

The separate SlotDesk Neon project contains `public.leads` with exactly these five columns. The intake login has INSERT permission and no SELECT, UPDATE or DELETE permission. The [server source](../backend/README.md), migration and six intake tests are included; no credentials are embedded in the extension or repository.

The owner configured the server environment variables and the Vercel intake is deployed at `https://slotdesk-leads.vercel.app/api/leads`. This preview is configured to submit there. An unavailable service leaves the original record in the account-bound browser queue. Retries preserve the first completion timestamp and the server ignores duplicate emails without changing the first saved choice. Public request checks and an isolated-database round trip passed; the first real registration from the updated extension remains to be observed. See [deployment verification](registration-deployment.md).

The final onboarding step shows the accepted notice and unchecked checkbox. Both Start using SlotDesk and I’ll add people later save the same five-field record; the checkbox is optional. Existing completed users see the notice/choice once before explicitly continuing; there is no undisclosed automatic backfill. Submission failure keeps setup usable. Settings shows pending/saved status and a retry action.

Owners view the private table through Neon. This implementation has no email/newsletter sending feature. Corrections, removal and opt-out requests go to the person who provided the private pilot. See the [shipped privacy notice](../extension/privacy.html).

## Browser-independent sign-in relay — 0.9.4.6

The new sign-in function can authenticate delivery of these same five user-confirmed fields from additional browser targets. It does not add token/calendar columns or change the optional updates choice. The existing direct Chrome intake remains. Tokens are handled transiently by the separate auth function and are never inserted into the leads database. [Connection design](google-connection.md) and [activation](browser-signin-setup.md).

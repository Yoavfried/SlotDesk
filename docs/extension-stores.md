# Extension-store readiness

Prepared for **0.9.4.6**, 21 October 2026. No submission, publisher account purchase, public visibility change or store approval is claimed. Packaging and Google OAuth activation do not establish store eligibility.

| Channel | What is reusable now | Still needed before submission/distribution |
| --- | --- | --- |
| Chrome Web Store | MV3 Chromium ZIP, narrow host permissions/CSP, pinned pilot identity, bundled source/fonts, local privacy/help, credits/changelogs | Publisher registration/verification and current fee/account requirements; store-issued identity/update plan; branded raster icons, screenshots/promotional assets and listing copy; public support/contact/privacy URLs; permission and data-use declarations including hosted sign-in and required registration; reviewer access instructions that preserve closed-beta restrictions; Google production/verification work as appropriate. No manifest icons/listing media are supplied as submission-ready by this release. |
| Microsoft Edge Add-ons | Shared Chromium UI/core and independent sign-in (Edge does not support the old Google getAuthToken path) | Partner Center publisher registration/verification; Edge identity/return registration; required logo/promotional assets and privacy/support/listing fields; certification, reviewer access, actual release/update test. |
| Firefox AMO, listed or unlisted | Separate background/sidebar manifest, stable add-on ID, unsigned XPI and built-in data categories for authentication/personal information/communications | Actual Firefox and ESR checks; resolve/review the 68 warnings from zero-error `web-ext` validation; Mozilla signing even for ordinary private self-distribution; reviewer/source instructions; listed/unlisted choice and update route; permission/privacy/consent review. Required onboarding registration for analysis is ancillary data: confirm Mozilla permits the actual consent/collection contract, and change it with owner approval if needed. The new manifest categories alone do not settle that policy question. |
| Safari / App Store | Shared source preparation with unsupported Chrome keys removed | Separate authentication bridge (for example a supported native authentication session with a reviewed callback handoff), Apple Developer enrollment, App Store Connect packaging/signing/app identity, privacy metadata/assets/review, real macOS/Safari tests. Apple's web-extension packager may avoid local Xcode packaging, but cannot supply missing runtime auth or device testing. iOS/iPadOS is separate. |
| Opera Add-ons | Shared Chromium package/core with full-tab fallback | Actual Opera/GX verification and manifest/sidebar adaptation if needed, developer registration, license/distribution choice, listing/icons/screenshots, policy review and moderator approval. Chrome Web Store installation in another browser is a different delivery route, not Opera catalog approval. |
| Brave / Vivaldi through Chrome Web Store | Same Chromium store route in principle | Actual current-browser sign-in/privacy/sidebar/install/update validation. They do not gain a support claim merely because Chrome accepts a ZIP. |

## Common blockers and decisions

1. Activate the server-side Google Web client using [the consolidated guide](browser-signin-setup.md); retain the approved test audience. Store review, OAuth verification and workplace administration are three separate approvals.
2. Publish an accurate reachable privacy notice/support contact for review. Explain that Google codes/tokens pass transiently through the auth service, calendar operations stay direct to Google, local credentials are session-only, and the leads table receives the five user-confirmed fields. State required registration and the separate optional updates checkbox accurately. Review each store's data/consent policy before submission; do not silently relabel or remove the agreed leads feature.
3. Choose the project software/distribution license and final listing/publisher names. Preserve both GitHub credits, [Website name TBD] and third-party font/data notices. The repository remains private until a separate owner decision.
4. Prepare brand-consistent toolbar/listing raster icons and genuine synthetic-data screenshots. Existing in-app wordmark/design-kit assets remain authoritative; do not invent a different logo or substitute private calendar screenshots.
5. Record each store-issued extension ID, corresponding exact OAuth return/origin and update origin. A new origin does not automatically inherit local profiles; provide the existing portable-configuration route if identity changes. Never put client secrets or Google credentials in a store package.
6. Validate install → update → account switch → browser restart, native sidebar/full-tab behavior, permission cancellation/revocation, file/clipboard fallbacks and shared-window write guards on the intended browser/OS. Include synthetic integrity cases and one controlled real-provider sign-in check. Provide reviewers a functioning approved route; do not bypass Google's test audience.
7. Before wider rollout review service capacity, hosting-level abuse limits, key rotation, credential-free operational logging and support. Current per-instance throttles are coarse, not global rate enforcement. Future public scale and any Google quota/billing policy need a current separate assessment.

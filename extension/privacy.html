Privacy notice

SlotDesk private calendar pilot · Updated 28 October 2026

SlotDesk reads calendar information to suggest meeting times. You review each new invitation and each individual meeting change before Google is asked to send updates.

What stays in your browser

Email guests without saved profiles, their confirmed meeting-only timezones and participant-specific preferences are saved with the unfinished draft and cleared after confirmed creation or starting a new draft. During your own-profile setup, SlotDesk may suggest your name from organizer or attendee details matching your email in selected calendars. You can edit the suggestion before continuing. This uses the existing Calendar permissions. Your saved profiles include names, email addresses, confirmed timezones, calendar mappings and any availability, travel, working-time or event-treatment rules you enter. SlotDesk also saves preferences, your selected participants and the invitation details you enter in review, including title, times, calendar, Meet choice, description and location. This lets you continue an unfinished meeting in another SlotDesk window or after reloading. Account settings are kept separately for each connected Google account; time display and appearance are shared across SlotDesk in the browser.

Decline alerts retain limited guest response and dismissal metadata, occurrence identifiers and expiry. Appointment follow-ups retain calendar/event identifiers and the chosen interval to protect during replacement searches. A pending reschedule retains account/calendar/event identifiers, the current version and before/after times, without the fetched title, description, guest list or video link. A pending detail edit saves your newly entered text and explicit guest additions/removals/role changes, with target identifiers, version, unchanged time and verification fingerprints. It does not save the fetched original title, description or full guest metadata. Completion removes the pending edit. Calendar-change alerts retain the meeting title, calendar/event and operation identifiers, verification status, check timing and a short result message. The latest 20 are kept; completed alerts can be dismissed. Unconfirmed changes are checked automatically only while SlotDesk is open and connected. Checks do not resend calendar changes. If you resolve an uncertain action manually, recovery history keeps the exact outgoing operation and your reported result. A manual report is labelled separately from Google confirmation and is never an automatic resend.

If a send needs confirmation, the prepared outgoing invitation is saved so SlotDesk can check the same event instead of creating a duplicate. This may include its title, recipients, dates/times, description, location and calendar/event identifiers. It is removed from the saved workspace after completion is confirmed.

These settings use local browser storage. SlotDesk does not encrypt them. Someone with access to the same browser profile or device may be able to access them, so use a protected browser and device for sensitive scheduling information.

Calendar data and Google access

Calendar lists, fetched events and free/busy information are held in session memory while you work. During setup and in Settings → Calendars, you choose which calendars SlotDesk can use. Events and free/busy data from calendars you leave out are not loaded or used for scheduling, suggestions or alerts. Calendar names remain available to change your selection. Existing meetings loads and caches your selected workspace calendars for the chosen dates; its calendar picker only filters that cache. Calendar selection and display-timezone changes use that memory cache; date changes and Refresh meetings load it again. Fetched calendar events are not saved in SlotDesk’s settings. Familiar-face suggestions cache only derived names, emails and ranking counts/timestamps locally, separated by account and selected calendar scope. Their 30-minute expiry extends whenever Manage profiles is entered before expiry; expired candidates are discarded on the next read. Disconnect, Clear data, changed source selection and confirmed access loss remove this candidate cache. Full event bodies are never included. Disconnect clears this cache in affected windows. Calendar details can include appointment titles, attendees, locations and descriptions where Google grants access.

Windows in the same browser share saved workspace changes and the connection status. Opening another SlotDesk window can use the already authorized Google connection; each window checks the connected account through Google Calendar. The saved connection status contains the account and a connection flag, not an access token.

The independent Google connection uses a SlotDesk service hosted on Vercel to exchange an authorization code and refresh Calendar access. The client secret stays on that service. Access tokens and an encrypted refresh-session envelope with its proof stay in browser memory/session storage, not workspace settings, backups or the leads table. They clear when the browser closes; reconnect to continue. The service caps sessions at seven days during this beta. While that service is inactive, the legacy Chrome connection uses Chrome’s managed token cache. SlotDesk does not save passwords. Workspace selection limits what SlotDesk uses; it does not narrow Google’s underlying permission grant. The configured permission allows viewing and managing events on accessible Google calendars. Existing users confirm their selection after upgrading; an already reviewed unfinished operation may read its exact target for recovery before that selection is completed. The current application creates reviewed new events and can change the start/end or supported details/guests of one existing appointment after review. Recurring changes affect one occurrence only. It has no event deletion or calendar-move feature.

Local backup and profile files

Backup and export create local JSON files containing the selected saved profiles, calendar assignment references and all their scheduling/travel settings. A full backup also contains workspace/display preferences and global time rules. These files are not encrypted. They exclude Google credentials, loaded appointment content, registration records, meeting drafts, calendar-change recovery and suggestion caches. Temporary flight/travel forms are never stored for later completion. The separate Download saved data action shown for an unreadable workspace exports the raw local workspace for recovery. That file may contain unfinished invitation details, registration metadata and recovery history. Treat it as sensitive; it is different from an ordinary backup.

Import/restore reads the file on your device and may check calendar metadata with Google to identify access problems. It does not change calendar appointments or sharing, upload the file or submit another person’s registration. Restore replaces local setup after confirmation; an optional current backup can be downloaded first. A temporary rollback record exists only while replacement completes or recovers from interruption.

What is sent and where

SlotDesk makes authenticated Calendar API requests to Google to read available calendars and events, check availability, create the invitation you review and apply an individual meeting change you confirm. Create & send invitations sends the reviewed event to the selected calendar and asks Google to notify every retained participant. Google Meet is requested when you enable it for a new meeting. Reschedule & notify guests sends only the selected event’s start/end change and asks Google to notify its retained guests. Edit meeting sends only changed title/location/description and, when explicitly edited, the verified complete guest list. Retained guest responses and other untouched details are kept. Guest removal withdraws that invitation and may remove it from the guest’s calendar; the organizing appointment remains. Existing video fields are kept. Decline alerts update when calendars are read/refreshed; they do not move meetings automatically or poll in the background.

SlotDesk has a separate registration intake component, described below. It has no cloud settings sync, email-reading feature or LLM service. Calendar information is not sent to the registration database or a model provider. Google authorization codes/tokens pass transiently through the separate sign-in function on the same Vercel hosting project for exchange/refresh. That function does not store tokens in Neon or intentionally log credential payloads. Calendar reads and reviewed writes go directly to Google. The new sign-in path can authenticate delivery of the registration fields described below; it does not add calendar data to that record. Copy meeting details places those details on your clipboard when you choose that action.

Hosting request information

Vercel processes connection information such as IP addresses, browser request headers and request URLs. Hosting logs may include the short-lived authorization code and encrypted state in a Google sign-in callback URL. SlotDesk does not intentionally write Google tokens, registration bodies or calendar contents to application logs. Short-lived, per-instance request counters limit repeated requests; these are separate from the leads table. Hosting providers apply their own infrastructure logging and retention policies.

Your onboarding registration

When you finish setup, SlotDesk saves the email, name and chosen timezone you confirmed, the browser name reported by your browser, the UTC setup-completion time generated by the app, and whether you checked the optional project-updates box. The checkbox is unchecked by default. In Chrome and Edge, a registration is recorded whether or not you choose updates. In Firefox, sharing the registration record is optional and off by default. SlotDesk asks for Firefox’s data-collection permission when you opt in; calendar use does not depend on it. The updates checkbox remains separate.

These fields are used to understand registrations and improve the product. They are sent over HTTPS to a private SlotDesk leads table hosted on Neon through Vercel. If the service is unavailable, the registration stays queued in your browser. Settings shows whether the registration has been saved by the service or is waiting to be sent. Failed submissions keep the original setup time and retry without blocking calendar use. In Firefox, retries require both your saved sharing choice and current browser permission. You can turn off future sharing in Settings → Registration sharing or Firefox’s add-on permissions. This does not remove an already submitted record or revoke an earlier updates choice; email support@buildwithspeedy.com for removal or opt-out.

Only project owners can view the private table. Each completed onboarding creates a separate record, including when you use the same email in another browser or installation. Retries of the same submission reuse its onboarding identifier and do not create extra records. Later profile edits do not change saved leads. A random onboarding identifier distinguishes submissions; it is not a device identifier. Only the browser name is saved, without its version or full identification string. A browser that hides its brand may be recorded as Chromium or Unknown. Older registrations without browser information show Unknown. No calendar appointments, Google access tokens, other people’s profiles, travel rules or meeting drafts are included. The service does not send emails. If you opted in, the owners may use your address for occasional updates about SlotDesk and their future projects; you can opt out at any time by emailing support@buildwithspeedy.com.

Registration records have no automatic expiry in this preview. Removal requests also cover managed copies; deleted records may remain in provider recovery history until its retention window expires. Email support@buildwithspeedy.com to request a correction, removal or opt-out. Clearing browser data or disconnecting Google does not remove a record already saved in the private leads table. Browser data removal can remove an unsent queued registration.

Disconnecting and removing saved data

The exit icon beside your email disconnects Google, closes editors and clears loaded calendar/review information from the current SlotDesk window. It clears the background Google session and memory-only credential storage. For the legacy Chrome connection it also asks Chrome to clear its cached sign-in tokens. Other open SlotDesk windows for the same account receive the disconnect and clear their displayed session too.

Disconnect keeps saved profiles, preferences and unfinished invitation details for recovery. Settings → Clear data removes the connected account’s saved workspace. An unfinished send or meeting change must be resolved first to avoid losing duplicate-send protection. This action does not delete calendar appointments. Display preferences are stored separately.

Disconnect does not revoke the app’s existing Google consent grant. Remove that grant through your Google account’s app-access controls if you want to revoke it.

Trips

Saved trips, flight times, locations, timezone changes and links to matching calendar entries stay in this browser as profile settings. Backups and exported profiles include those settings. Flight estimates use bundled airport data locally; no flight service receives your route. Possible-flight and source-change checks use the selected calendars already available to SlotDesk. Trip actions never change calendar appointments.

Connection support

Help → Connection details shows the build, browser capabilities, package identity and connection-service readiness. Copying these details does not send a report and includes no account email, Google tokens or calendar contents.

Using a work account

Use SlotDesk with workplace calendars only when your organization permits the extension, requested Google permissions and local data handling. Email support@buildwithspeedy.com if you have questions about SlotDesk’s configuration.
